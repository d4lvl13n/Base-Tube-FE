# Thumbnail Studio frontend

The implementation uses `/api/v1/thumbnail-studio`. Per spec §17 (26 September 2026) the Studio replaces the old web generator: there is no dark launch and no fallback to the old signed-in generator.

## Entry: `/ai-thumbnails/generate`

`GeneratePage` only routes, and never reads `/capabilities`:

- signed-in creator (Clerk or wallet) → `StudioCreatePage`;
- visitor without an account → `VisitorCreatePage`;
- account still loading → "Loading your account…". For wallet accounts this includes the moment a stored session is being restored (`isRestoring` from `AuthContext`, true from the first render until the stored session is read): `useCTREngine` reports neither authenticated nor anonymous, so `VisitorCreatePage` never mounts (and cannot overwrite a saved `?draft=`) before `StudioCreatePage` can restore it.

`ThumbnailBriefForm` is shared by both create screens and the project brief (`BriefReview`). On `StudioCreatePage`, the primary button reads "Generate N concepts · X credits" (X from the pricing catalog, below). One click saves the brief as a project and opens it on step 2 (Choose) with `studioEntry.startGeneration` and the price shown (`generationCredits`); the project page starts that generation once on arrival (quote + start, below) and shows its running work under a short brief summary with "Edit brief". The flag is consumed with `replace` before the start, so Back, a reload or a sign-in return never starts it again. A short balance or paused starts disable the button before the click (same notices as every priced button), and the project page does not start in those cases either. The YouTube, script and image sources open their panel on the brief instead. The unsaved create form (brief, concept count, quality) is kept per account in `sessionStorage` (`saveStudioCreateDraft` in `utils/studioDraft.ts`), restored after a reload, cleared once the project exists, and can be discarded.

After a sign-up or sign-in, a brief the visitor wrote in this tab (`studioDraft`, the active draft or `?draft=<id>`) fills the signed-in create form (`studioBriefFromDraft`: title, hook, description, visual direction, format, composition, text choice; the concept count; quality High) and becomes that account's create draft; the visitor draft is then cleared. Nothing is saved as a project or started before the creator clicks "Generate N concepts · X credits" (one click, as above). While the welcome credits are not in the balance yet (confirming, or deferred to another day), the button shows the usual "Not enough credits — you have Y · Buy credits".

"Create a new thumbnail for this video" (audit result) calls `studioCreateUrlForTitle`: signed in, it writes the create draft with the video title and opens `/ai-thumbnails/generate`; without an account, it writes a visitor draft and opens `/ai-thumbnails/generate?draft=<id>`, which the visitor page reads.

## Visitors (owner decision, 28 September 2026)

Visitors cannot generate images: there is no anonymous generation, no free generation quota and no claim of free images after sign-in. The web app embeds no API key and never calls `/v1/images` (FE-24). The `/api/v1/thumbnail-studio/anonymous/*` client, its hook and polling, the concept grid's anonymous mode and the claim coordinator are gone.

- `VisitorCreatePage` shows the same creation form (`ThumbnailBriefForm` without the account-only pickers: title, hook, description, visual direction with the text choice — suggestion, exact words, no text — format, composition, concepts 1–3). The brief is kept in this tab (`studioDraft`, 24 h), restored after a reload and discardable; `?prompt=` fills the title.
- Its one button, "Create a free account to generate", saves the brief and opens the account gate in place with reason `generate` (below). It never calls a generation route. Under it, from `GET /api/v1/tool/welcome-offer` (public, `useWelcomeOffer`, 5 min): "New accounts get {credits} free credits — enough for one generation, one edit and an audit."; with `available: false`: "Today’s welcome credits are all given — create your account now and get them tomorrow."; while the offer is unknown (loading, failed): "New accounts get free credits." with no number. The "enough for…" phrase is fixed copy (50 credits at the 28 September prices: 2 concepts 30 + edit 18 + audit 2).
- Visitors keep the free thumbnail audits (3 a day, `/ai-thumbnails/audit`). A 429 `ANONYMOUS_AUDIT_CAPACITY` (the platform's free audits for today are used up) says "Free audits are used up for today. Create a free account to get {credits} credits." (no number while unknown; "…to keep auditing with credits." when today's welcome credits are all given) with "Create a free account", which opens the gate with reason `audit_capacity`. The per-network 429 `ANONYMOUS_AUDIT_QUOTA_EXCEEDED` keeps its own message.
- The shared `api` client never replays a 429 whose code is a spent allowance (`ANONYMOUS_AUDIT_CAPACITY`, any `…QUOTA_EXCEEDED`): waiting a few seconds cannot bring it back.
- The sidebar shows a visitor (signed out, once Clerk and a stored wallet session are known) no create allowance: "{audit limit} free audits a day" with "{remaining} left today" (the audit allowance from `GET /ctr/quota`) and the link "Create a free account — {credits} free credits" to `/ai-thumbnails/sign-up` ("free credits" while the offer is unknown; "Create a free account" with the "all given" line when unavailable). Collapsed, the same as an audit ring and an account icon link. Signed-in accounts keep their balance or quota as before.
- The landing page FAQ ("Is it free to try?") says the same: up to 3 free audits a day without an account; generating and editing need a free account, whose welcome credits come from the offer. "Can the AI generate thumbnails based on my audit results?" describes the current flow: "Create a new thumbnail for this video" opens the Studio's create screen; an existing thumbnail is fixed in the Studio with "Apply N corrections · 18 credits".

## Sign-in and sign-up (owner decision, 28 September 2026)

AI Thumbnails has its own sign-in and sign-up pages. Same Clerk instance, users, credits and roles as base.tube; only the pages, their copy and where they go afterwards differ. base.tube's `/sign-in`, `/sign-in-web3`, `/sign-up` and onboarding behave as on `main` (they no longer read `studioReturn` or `studioDraft`). No other Clerk window or custom login exists.

- `/ai-thumbnails/sign-in/*` and `/ai-thumbnails/sign-up/*` (`CTREngine/auth/AIThumbnailsAuthPage.tsx`): the AI Thumbnails header, a short value column (Create, Fix, Audit; the sign-up page adds "{credits} free credits once your email is verified." from the welcome offer, "Free credits once your email is verified." while it is unknown, or the "all given" line) and Clerk's `<SignIn>` / `<SignUp>` with `routing="path"`, so Clerk's steps (`verify-email-address`, `factor-one`, `sso-callback`, `continue`, …) are sub-paths of the page. The components (`CTREngine/auth/AIThumbnailsClerk.tsx`) have the AI Thumbnails look (adapted from base.tube's sign-up look) and fixed props: `forceRedirectUrl` and the other flow's force URL (`signUpForceRedirectUrl` / `signInForceRedirectUrl`) are `/ai-thumbnails/auth/continue`, `signUpUrl` / `signInUrl` the other AI Thumbnails page.
- The sign-up page has the gate's unticked opt-in box ("Send me occasional product tips and updates. Optional — you can unsubscribe any time."). Its value is stored at once (origin marker below; also the gate record when the gate started this sign-up, whose box it shows), so it is known before the form is sent.
- The sign-in page has "Sign in with a wallet": the existing `ConnectWalletButton` flow. `useWeb3Auth` does not navigate after a wallet sign-in on `/ai-thumbnails/sign-in` (elsewhere it still goes to `/` or `/onboarding/web3`); the page sends the signed-in wallet to the continue address. Entries marked "wallet" (`state.wallet`) scroll to and focus that section.
- The after-auth target is a constant, never read from the URL: Clerk keeps only its own query parameters from one step to the next (the old `studioReturn`/`studioDraft` were dropped on `/sign-up/verify-email-address`), and it ranks its redirect query parameters above the component's props. So before Clerk renders, the pages drop any Clerk redirect parameter (`redirect_url`, `after_sign_in_url`, `after_sign_up_url`, `sign_in_force_redirect_url`, `sign_in_fallback_redirect_url`, `sign_up_force_redirect_url`, `sign_up_fallback_redirect_url`, also inside a `#/…?` Clerk hash route) that is not the continue address (`cleanStudioAuthUrl`). A visitor already signed in when the page loads (Clerk), or a wallet, goes straight to the continue address; a Clerk sign-in finishing on the page is left to Clerk's own redirect (no second continue).
- Origin marker (`utils/studioAuth.ts`, `sessionStorage['thumbnail-studio:auth-origin:v1']` = `{destination, intent: 'sign-up' | 'sign-in', consent?, startedAt}`): every AI Thumbnails entry writes it (`startStudioAuth`: the header and page sign-in choices, the landing page "Sign In" and "Get Started", the gate's two choices); it also saves the visitor's brief on screen (`SAVE_STUDIO_DRAFT_EVENT`) and notes the welcome card. Each auth page (and each Clerk step, which reloads the page) refreshes it with its intent, or writes one with the default destination when missing (`touchStudioAuthOrigin`). `destination` must pass `studioReturnDestination` (AI Thumbnails pages, `/ai-thumbnails/audit` included; never the auth pages); a marker is valid 30 minutes after the last auth screen.
- `/ai-thumbnails/auth/continue` (`AIThumbnailsAuthContinue`): reads the marker once, clears it and goes to its destination with `replace` (default `/ai-thumbnails/generate`, whose create form restores the tab's visitor brief, the active `studioDraft`), never through base.tube's onboarding. For a Clerk account with a valid marker whose intent is `sign-up`, or whose account was created in the last 10 minutes (a new Google or Discord account made on the sign-in page), it arms the welcome credits confirmation (`armStudioAuthConfirm`: a closed gate record `awaiting_sign_in`, reason `account`, with the marker's consent and `startedAt` as `signUpStartedAt`), unless the gate has its own pending record. A PENDING wallet account first gets `POST /api/v1/web3auth/onboarding/complete` silently (`finishStudioWalletSignIn`, once per account at a time; the account keeps its temporary `0x_…` username); on failure it logs the error and still goes on (the account stays PENDING and can complete later on `/onboarding/web3`). - Welcome credits: every AI Thumbnails sign-up (the sign-up page or the gate) confirms once, with the gate's result handling (below). The AI Thumbnails sign-in page (existing accounts) confirms nothing, unless the gate started the sign-in.
- Every AI Thumbnails entry points to these pages: no AI Thumbnails link leads to `/sign-in`, `/sign-up` or `/sign-in-web3`.

## Account gate (FE-22, QA-05: the AI Thumbnails sign-up in place)

`EmailGateModal` is rendered by `StudioFunnelBridge` in `App`, above the routes, and is driven by one record per tab in `sessionStorage` (`utils/studioFunnel.ts`), so it survives the switch from `VisitorCreatePage` to `StudioCreatePage`, the remount of the whole app on an identity change (`AuthCacheBoundary`), the AI Thumbnails sign-in and sign-up pages, the continue screen and full-page redirects (Clerk's steps, Google, Discord). It asks for no email: the account's own verified email decides the welcome credits on the server. States:

```
form ──"Create my free account"──▶ awaiting_sign_in ──signed in (any method)──▶ confirming ──▶ granted
 │     or "I already have an account" │  (flow sign-up | sign-in,          POST /tool/      │  (already granted:
 │     (consent kept)                 │   consent, signUpStartedAt)         email-capture/   │   closed, no message)
 └ closed: forgotten                  │ Back: to the offer                  confirm, once    └▶ refused
                                      │ closed: kept, hidden                                    (retry unless final;
                                      └ reopened where it stopped                               closed: kept if it
                                                                                                can be retried)
```

- `openEmailGate(reason)` opens it on the offer (`generate`, `edit`, `audit`, `save`, `audit_capacity`; `account` is the sign-up page's confirmation): the title says why an account is needed ("Generating needs a free account", …, "Free audits are used up for today"), one line offers "New accounts get {credits} free credits once the email is verified." (the welcome offer; "free credits" without a number while unknown; the "all given" line when unavailable), an unchecked "Send me occasional product tips and updates" box (`marketingConsent`), the primary "Create my free account" and the secondary "I already have an account". A gate already waiting for its sign-up or sign-in reopens there. Records saved with the old reasons (`quota`, `network`, `capacity`, `busy`, `share`) are read as `generate` (`save` for `share`), so a pending sign-up still confirms.
- Both choices save the visitor's brief and write the origin marker with this page and, for the sign-up, the consent (`startStudioAuth`), then save `awaiting_sign_in` with the flow, the consent and, for the sign-up, `signUpStartedAt` (`startEmailGateSignIn`). "Back" returns to the offer with the box as it was (`backToEmailGateOffer`).
- "Create my free account" shows the AI Thumbnails sign-up in the window (`AIThumbnailsSignUp`, the component of `/ai-thumbnails/sign-up`, with `routing="virtual"`); "I already have an account" shows the AI Thumbnails sign-in (`AIThumbnailsSignIn`) and "Sign in with a wallet", a link to `/ai-thumbnails/sign-in` opened on its wallet section. Both end on `/ai-thumbnails/auth/continue` (fixed props, above), which returns to this page; Clerk's own "Sign in" / "Sign up" links open the other AI Thumbnails page.
- Google and Discord: in place, Clerk handles the email and its code; its social buttons are hidden (`appearance`) and "Continue with Google or Discord" opens the full AI Thumbnails page of the same flow (the marker and the gate record are already written; the sign-up page shows the gate's box). Why: in `virtual` routing, clerk-js 5 builds a sign-up's provider return (`ssoCallbackUrl`) from ClerkProvider's `signUpUrl` or else the dashboard's (`displayConfig.signUpUrl`: the Account Portal in development, `https://beta.base.tube/sign-up`, base.tube's `SignedOut` page, in production), and its "continue" step (the development instance's username) goes there too. On the full pages (`routing="path"`) both are sub-paths of the AI Thumbnails page (`/ai-thumbnails/sign-up/sso-callback`, `/ai-thumbnails/sign-up/continue`, `/ai-thumbnails/sign-in/sso-callback`) with the fixed targets. The in-place sign-in would return through its `signUpUrl` (the AI Thumbnails sign-up page) but hands off the same way, so both behave alike. ClerkProvider keeps no `signInUrl`/`signUpUrl`: base.tube's pages and modals are unaffected.
- After the sign-up or sign-in (and after a sign-up on the AI Thumbnails sign-up page, armed by the continue screen), the bridge calls `POST /tool/email-capture/confirm` exactly once (single flight; a reload during the call sends it again, the server is idempotent), with `marketingConsent` always as a real boolean (the box), the pending referral code (`pending_referral_code` in localStorage, from any `?ref=` link) only when this tab started the sign-up from the gate within the last 30 minutes (`GATE_REFERRAL_WINDOW_MS`; omitted otherwise, cleared once sent), and the fingerprint. No `POST /tool/email-capture` is sent any more, and no email is compared (the FR-11 email match is gone). A call without an answer after 20 s is a retryable failure (`TIMEOUT`). The visitor stays on the page (the create page shows the restored brief).
- Results: granted → "{credits} credits added" (`signupCredits`) and "You now have N credits." (`balance.available`; the balance is an object `{balance, reserved, available}`, a number from older servers); deferred (`granted: false, deferred: true`, today's welcome credits all given) → "Today’s welcome credits are all given. Your {credits} credits will be added on {grantOn}." (`grantOn` as "29 September"; a date without a time is that calendar day; "tomorrow" when missing), with Continue, no retry and no reminder; already granted (a repeat call answers `granted: false, alreadyGranted: true`) → the window closes without a message; `EMAIL_IN_USE` → the server's message (the fixed "This email is already linked to another base.tube account, so its welcome credits were already used." when it has none), final: no retry, no reminder; `EMAIL_DISPOSABLE` → "Welcome credits need a permanent email address." (final); `WELCOME_LIMIT_NETWORK` → "Welcome credits are limited per network. You can still buy credits." (final); `EMAIL_NOT_VERIFIED` with `web3_no_email` → "not available for wallet accounts" (final); `email_not_verified` → "not verified yet … Try again"; `verification_check_failed` / `user_not_found` → "could not check your email address just now"; `ACCOUNT_BANNED` → "not available for this account" (final); network, timeout, 401, 5xx (a server error's text is never kept or shown) → "We could not add your credits yet. Try again in a moment." with Try again. The balance is refreshed after a grant.
- Closing a refused gate that can still be retried keeps it (hidden). While it is kept (24 h), the AI Thumbnails pages show a small reminder, "Finish claiming your {credits} free credits" (the welcome offer; "your free credits" while unknown), which runs confirm again and reopens the gate with the result; Dismiss hides it until the next page load.
- A sign-in elsewhere (the AI Thumbnails sign-in page from the header, base.tube's pages, a wallet) while the gate only showed its offer never calls confirm. The gate is hidden on the sign-in, sign-up, continue and onboarding screens (base.tube's and AI Thumbnails').
- Accessibility: every step (including one restored after a redirect) moves focus to its heading or main action, never taking focus from another open window. Tab stays inside (the in-place sign-up included); Escape closes the gate only from inside it; while open, the app root (`#root`) gets `inert` and `aria-hidden` (the window is outside it); focus returns to the opener on close.

Every AI Thumbnails entry and auth page notes it in the tab (`noteStudioAuthStart`, sessionStorage, kept through Clerk's steps and redirects); a PENDING wallet account is noted by account. On an AI Thumbnails page the card opens only for a new account: a Clerk account created within the hour (`createdAt`), or the noted wallet account. An existing account signing in never sees it. Once per account on this browser (localStorage); once open it stays in the tab across pages and the reload Clerk does right after a sign-up, until Close (or an hour). It says "Welcome to base.tube AI Thumbnails"; "{credits} credits added." only when the welcome credits confirmation (after the gate or the sign-up page) granted them in this tab (`granted: true`); "Your welcome credits arrive on {date}." when it deferred them (`noteStudioWelcomeDeferred`); and the link "Set up your channel style" (`/ai-thumbnails/settings/style`). It never blocks the page.

## Sign-out and another account on the same browser

The browser keeps the last signed-in account (`thumbnail-studio:funnel-account:v1`, localStorage), so a sign-out or a switch is seen even across full-page reloads (a wallet session being restored is never taken for a sign-out). Either one clears the gate record, this tab's visitor drafts and the welcome card (`forgetStudioFunnelForAccountChange`); a confirmation still in flight is ignored. The next account never confirms for the previous visitor, and the next visitor never sees the previous brief.

## Routes

Studio pages are lazy-loaded (`App.tsx`) under one route family:

- `/ai-thumbnails/projects`: saved projects; "Create a thumbnail" opens `/ai-thumbnails/generate`. Each card has a secondary "Hide from list" (the server's archive flag, `PATCH {archived: true}` with a fresh `lockVersion`); "Show hidden projects" lists them too, marked "Hidden", with "Show in list". A hidden project opens and works normally: starting any work in it (or importing an image) restores it on the server.
- `/ai-thumbnails/projects/:projectId`: source review, brief, profiles, operations, versions, audit corrections and export.
- `/ai-thumbnails/projects/profiles` redirects to `/ai-thumbnails/settings/style` (query kept, so `?profile=<id>` still opens that profile).
- `/ai-thumbnails/projects/batch?projects=<comma-separated UUIDs>`: up to three projects, one or two concepts each, one selected image per video in the ZIP.
- `/ai-thumbnails/studio/*` redirects to the same path under `/ai-thumbnails/projects` (query and state kept). Auth return paths using the old name are normalised.
- `/ai-thumbnails/sign-in/*`, `/ai-thumbnails/sign-up/*` and `/ai-thumbnails/auth/continue` (eager, not lazy): Sign-in and sign-up, above.

Private Studio pages wait for the account to load (`StudioAuthGate`), including a wallet session being restored, before showing sign-in choices, so a signed-in creator never sees a sign-in prompt flash. The sidebar always lists Projects (sign-in required).

## Settings hub

`/ai-thumbnails/settings/:section` (`SettingsPage`, sections in `components/settings/settingsSections.ts`) is the one place for creator settings; `/ai-thumbnails/settings` opens Channel style and an unknown section redirects there. A left section list (a scrolling row on mobile) and the section content:

- `style`: the channel profiles (`ChannelProfilePanel` without `onApply`: cards with colours, language, font and headline mode; `?profile=<id>` opens that profile's editor) and the thumbnail styles saved from results (`/api/v1/ctr/styles`, list and remove; hidden when there are none).
- `logos`: each profile's logo, replaced or removed in place (`POST /thumbnail-studio/assets` with purpose `logo`, then `PATCH /profiles/:id` with the full settings and `If-Match`). There is no account-wide logo list on the server.
- `face`: the face reference used by "Include my face" (`/api/v1/ctr/face-reference`, unchanged behaviour).
- `preferences`: language, headline mode and content rules per profile (they are profile-level; no account-wide preference exists), each row linking to that profile's editor.
- `credits`: available and reserved balance, the live prices (`useStudioPricing`), Buy credits, and purchases, bonuses and refunds from `GET /credits/ledger?limit=100` (reservations and captures for work are left out; only the newest 100 ledger rows are read).
- `account`: links to `/profile` and, for email accounts, `/profile/settings`; nothing is duplicated.

The sidebar's Settings entry stays active on every section, and its credit balance links to `settings/credits`. Sign-in and checkout return to a settings section (`studioReturnDestination` allows the six section paths).

`BuyCreditsModal` renders in a portal on `document.body` (z-index above the helper and sticky bars), centred and scrollable. Each pack shows its full name, credits, what it buys at the live prices ("≈ 13 concepts · 11 edits · 100 audits": concept `ctr.generatePerConcept`, edit `thumbnail.editPerImage`, audit `ctr.audit`) and the price per credit. The best-value pack starts selected; one button, "Continue to secure checkout · <price>", opens Stripe Checkout with the existing call and returns to the same page.

## Error messages outside the project screens

Channel audit, thumbnail audit, credits, settings and the `useCTREngine` banner use `plainApiError` (`utils/plainApiError.ts`): the server's `{error:{message}}` or `{message}`, else a plain sentence saying what happened and what to do. Axios wording ("Request failed with status code 503") is never shown; the status and code appear as a small muted suffix only when `NODE_ENV === 'development'` (`TechnicalErrorDetail`). A channel audit that does not finish (503, "The audit analysis did not finish. Please try again; no incomplete report was saved.") shows that message with "Try again", which runs the same channel again.

## Capabilities

`GET /capabilities` returns `{operations:{available, reason: null|'paused'|'worker_unavailable'}, validation, pricing, limits}`. Profiles, channel handoff and batch are always on. The frontend reads it through `useStudioStartAvailability` and `useStudioPricing`: an explicit `available:false` disables every priced button and shows, next to it, "Starting new work is paused for now / temporarily unavailable. Your work is saved…"; `pricing` (the catalog, falling back to the one in the shared balance read) gives the price on each button. Loading or failed capabilities never hide the Studio; the server still refuses a paused start (`503 STUDIO_PAUSED`). `validation: false` (the automatic check is turned off): versions show nothing about the check (`OutputWarnings checking={false}`). With the check on, a version shows only the checks that did not pass (each with "Is this issue present?"), nothing when every check passed or none ran, and one short line, "Automatic check unavailable for this image.", when it ran but could not check.

## One-click paid actions

Every paid or free action is one click on a button that shows its price. There is no price step, no "price ready" card and no confirmation of a price that matches the button.

| Action | Button | Price (`utils/studioPricing.ts`, from the catalog) |
|---|---|---|
| Generate (create page, project brief, "Your brief" card) | "Generate 2 concepts · 30 credits" | `ctr.generatePerConcept` × count; quality does not change it |
| AI edit (Refine step, "Change something") | "Apply edit · 18 credits" | `thumbnail.editPerImage` |
| AI headline change / removal (image without a text layer) | "Update text · 18 credits", "Remove text · 18 credits" | `thumbnail.editPerImage` |
| Audit corrections | "Apply 2 corrections · 18 credits" | one edit |
| Text layer (image with a text layer) | "Apply text · free", "Remove text · free" | free |
| Audit | "Audit this version · 2 credits" (3 with persona opinions) | `ctr.audit` / `ctr.auditWithPersonas` |
| Retry of a failed output | "Retry · 15 credits" ("Prepare concepts again · N credits" for a new group) | the output's action |
| Batch | "Generate all · 75 credits", each video showing "2 concepts · 30 credits" | sum of the concepts |
| Text assists | "Suggest two video titles · free", "Ask for style suggestions · free", "Request a suggested summary · free"; a script or image upload starts its suggested brief at once | free |

The quote (`POST /operations/quote`) stays the server's fixed-price and idempotency mechanism, but only inside the click (`useStudioOperation.run`, `StudioPaidAction`):

1. The page flushes the autosave first (`project.save()`), so the quote's revision is the current brief (no `BRIEF_CHANGED` from a pending save), and builds the request from the saved revision.
2. It quotes. When `quotedCredits` equals the price on the button, it starts at once: the Idempotency-Key is stored in `localStorage` before `POST /operations/:id/start` is sent, and storage that cannot keep it refuses the start.
3. When the quote's price differs (the catalog changed, or no price could be shown), nothing starts: one inline line says "The price is now X credits — Generate" (the verb of the action), and that click starts exactly the quoted work.
4. `BRIEF_CHANGED` or `QUOTE_EXPIRED` on start prices the same work once more against the current saved brief and starts it, inside the same click. If that is refused again, the button shows "Couldn't start — try again."
5. A second click while one is handled does nothing (one quote, one start); the button reads "Starting…".

Refusals and changed prices are kept per action key (`generate:2:high`, `edit:<version>:<target>:<words>`, `correction:<version>:<findings>`, `retry:<item>`…), so they show next to the button that asked, and a confirmation never starts a different request (the key includes the exact words). Before the click, the button uses the shared balance (`useStudioAvailableCredits` → `useStudioBalance`, never a quote-time snapshot): below the price it stays disabled with its price. The tool area around it (`StudioCreditsScope`: each project step, the ongoing-work list, the create page's Generate bar, the batch page) shows one notice, whatever the number of short buttons: "Not enough credits — you have Y" with a real "Buy credits" button that opens `BuyCreditsModal` (checkout returns to the same screen, where the refreshed balance re-enables the buttons and removes the notice). A `StudioPaidAction` outside any scope shows the same notice itself. After the click, refusals are mapped by code (`classifyStudioStartError`): 402 → the same single notice ("Not enough credits", without a count the stale balance would contradict) and a balance refresh; `STUDIO_PAUSED`/`STUDIO_UNAVAILABLE` → the saved-work message and a capabilities refresh; the generic codes of shared services (`FORBIDDEN`, `CONFLICT`, `UNPROCESSABLE_REQUEST`) use the page's own wording; network errors, 5xx and 429 say "You can retry this same start safely": the next click sends the same start (same operation, same key) and never a new quote, and the operation is read once, so work whose answer was lost but which did start appears. No message mentions a quote or a price step.

- Studio errors (QA-10, `studioError` in `api/thumbnailStudio.ts`, `studioTransportMessage` and `studioTechnicalDetail` in `api/studioErrors.ts`): the server's `error.message` when it has one (never the internal text of `INTERNAL_ERROR`), the page's wording for the generic codes, otherwise a plain sentence saying what happened and what to do: 401 "Your session has ended. Sign in again, then try again.", 404, 413, 429 with the wait, 5xx "The Studio could not answer just now. Your saved work is safe — try again in a moment.", no answer "We could not reach base.tube. Check your connection, then try again.", timeout "This is taking too long to answer. Try again in a moment.". Axios wording ("Request failed with status code …", "Network Error") and programming errors are never shown; a sentence raised by the page is. `studioError` keeps the HTTP status; `StudioErrorDetail` / `StudioErrorText` add "(HTTP 503 · STUDIO_UNAVAILABLE)" as a small muted suffix only when `NODE_ENV === 'development'` (the shared `TechnicalErrorDetail`). Every Studio error display uses them: project, create, projects, batch, brief references, sources, uploads, validation feedback, channel handoff, open-in-project, priced-button refusals (`StudioStartProblem` carries `code` and `status`) and the gate's refusals.
- a failed item explains its `errorCode` (`studioItemFailureMessage`): `PROVIDER_NOT_REACHED` says the image service could not be reached, nothing was created and the credits for this result were released, and that it can be retried; other codes keep "This result could not be completed. Other ready results are kept."

`StudioOperationPanel` shows started work only: its state ("In progress", "Ready", "Some results are ready", "Failed"; a quote has no label), charged and released credits, each output, "Review suggestion" for text assists, and a one-click Retry for a failed output. Keys are released once their operation finishes or no longer exists; the rest expire after 24 hours, at most 50 kept (channel handoff keys follow the same rule). Operation IDs are stored per account/project (or batch selection) once work starts. The page shows (`visibleStudioOperations`): running work; the latest finished work; and finished work holding a retryable failed output, until a retry of that output has run to the end (succeeded, or failed and holding its own Retry) or the creator uses Dismiss. A quote that never started is never shown; quote IDs stored by earlier versions are read once, hidden and removed from storage. The server's running operations supplement the stored IDs.

A started retry is linked to its failed output: `GET /operations/:id` items carry `retryOfItemId` (RB-08), and the browser also stores the link (`retryLinks`, per scope, pruned with the operation IDs) for older servers and for a new group that replaces a failed preparation. A finished retry releases the failed work's Retry entry. Polling is 2 s in the foreground and 10 s in the background; failed reads back off 2 s → 10 s → 30 s and a 404 stops polling and forgets the ID. Newly started work scrolls into view and receives focus once, only if focus is still on the button that started it or on nothing; a creator who moved on keeps focus. A polite live region announces starts ("2 concepts: started."), changed prices and state changes. After a start, the project and the project lists are read again (a start restores a hidden project).

The shared balance refreshes after accepted starts and settlement changes, on focus and across tabs. Background refresh failures keep the last balance silently, and loading state is shown for the first load only. If the first load fails, the sidebar says "Couldn't load your credit balance." with Retry (`useStudioBalanceLoadFailure`); the notice goes away once a read succeeds.

## Version, preview and export contract

Hydrated versions provide `asset` and `outputFormat`; the latter is the version's original revision format. Project GET additionally includes `selectedVersion`, even when it is older than the first history page. The comparison uses up to three versions of the same format and a shared title at 160 or 320 px. Preview does not call any paid endpoint.

Asset reads (`useStudioAssets`, also `ThumbnailPreview` and `AssetInput`) share one React Query key per asset and refresh their signed URLs a minute before `urlExpiresAt` (between 15 s and 4 min) and on focus. This covers project versions and brief references.

PNG, JPEG and ZIP downloads use server-created binary responses. A download does not select a version or imply publication. An export refused as JSON (for example `EXPORT_TOO_LARGE`) becomes a `StudioRequestError` keeping the server code, message and advice, which the drawer and cards display; no AI generation is used as a fallback. `EXPORT_TOO_LARGE` carries `details.suggested` (a format and size that fit): cards, the drawer and the batch ZIP offer "Download as JPEG, YouTube size instead" (or the suggested pair) in one click; the batch also switches its selects to it.

Uploads, thumbnail and legacy profile imports, YouTube source reads, file exports (60 per 10 min) and ZIP exports (also 10 per 10 min) turn a 429 into a `RATE_LIMIT_EXCEEDED` `StudioRequestError` with "Too many requests — try again in …" (`Retry-After`, else `RateLimit-Reset`, when the browser can read them; they are not CORS-exposed, so a cross-origin page says "in a moment"). The shared client does not replay a 429 on these routes (the limits count over ten minutes).

`POST /assets` is a multipart form of exactly two parts, `purpose` then `file`, with the multipart type set on the request: the shared client defaults to `application/json`, under which axios turns a FormData body into JSON (`{"file":{}}`). A script over 1 MB (checked before sending, or a 413) says "This script is over 1 MB. Paste an excerpt instead."; a 413 for a smaller script is the 100,000-character limit and says so.

The legacy audit routes answer `auditId: null` when the audit was returned but not saved (`types/ctr.ts`); nothing links to an audit from that id. `ctrApi.generateThumbnails` (backend route deleted, LG-01) and the unused `ctrApi.applyOverlay` are gone with their tests and MSW handler.

For supported checks with `status=warning`, creators can confirm "Issue is real" or contest "Not an issue" through the shared SDK's free `validation-feedback` PATCH. Failures preserve the previous response and expose retry. Feedback remains available while starts are paused and never blocks selection or export.
